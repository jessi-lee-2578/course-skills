# 系统二实验报告

开始前读取用户指定的记录或项目下的 .course-context/sys2-lab-report.md。长期设置更新到记录文件，正式报告只写实验要求的内容。

先读本次指导、源码、当前报告和用户的运行记录。已有教师模板或本人手改稿时就用它。没有指定时，先用 [系统二 Markdown 报告模板](references/report-template.md) 写一份可编辑的 Markdown 草稿。有多个独立小实验时可以按任务分章。报告具体内容由本次实验决定。PDF、代码包或其他交付物按当次要求制作。

写实验过程或验证结果前，打开 [实验记录与证据示例](references/debug-evidence.md) 并按本次实验筛选证据。成稿时打开并执行 [通用用语检查](../personal-writing/references/wording-check.md)。

## 实验过程中保留 Debug 素材

实验还在做时，就本次正在写或调的一步说明它和其他文件或运行阶段的关系，再引导用户亲自运行、读一次输出或波形，记下他看到了什么、怎么判断、最后怎样复测。每遇到值得写进报告的一处现象，可以留下最小记录「触发条件 → 证据 → 当时的判断 → 动过的代码 → 复测结果」。顺利通过的步骤可以写本人实际核对过的关键现象。

报告阶段优先从已有源码、命令、截图、日志和对话整理。缺关键本人素材时，就着具体信号、命令或错误问一两个问题，例如「你停在入口单步时，执行哪条指令以后寄存器才变？」用户已给足材料时直接组织。按 [实验记录与证据示例](references/debug-evidence.md) 选取本次真正需要的记录。

## 写成报告

- 解释改动时先写为什么改，从相邻接口或已有实现入手，然后给关键命令或代码位置。截图应对应一项具体观察，配文说清停在哪条指令、哪个寄存器或输出发生了什么。
- 对编译与调试结论，写出真实工具链、运行环境、命令和测试结果。区分静态反汇编显示的指令和单步实际经过的路径。报告若用日志或截图作证，保留其可追溯位置。待复现的步骤标清状态。
- 按本次报告模板回答思考题，先复述题目需要证明的东西，再给观察和解释。不要把某一学期的文件命名、实验环境和提交结构沿用成新作业的要求。
- 反思从作者真正遇到的情况写起。作者已经写了观察或感想，就沿用其原段落，只从停笔处补充发现和原理。比如作者说看见 GDB 的指令和反汇编文件很像，续写可解释两处指令来自哪里、为什么能借反汇编地址找断点。

正文用 [中文写作](../personal-writing/SKILL.md) 的通用规则和作者自己的措辞。用自然陈述交代做了什么、为什么、看到什么。术语、命令和信号名称准确保留。先改主线和推理，再改句子。聊天问答、临时检查清单和资料收集过程留在工作稿。

交付前检查 Markdown 的图片相对路径、图文对应、代码围栏、真实验证范围和本人手改段落。要导 PDF 时再检查图片和代码换页。报告和代码包的命名、目录和提交格式服从本次指导。
